# D007 · Paid batch mode via Stripe Checkout with a signed-cookie entitlement, no accounts
Date: 2026-09-12 · Goal: G-001 (svc-lab monetization diversity, A014) · Status: active (test mode; live keys pending Owner)
Context: Every svc-lab service was AdSense-only with $0 confirmed. The Owner has a Stripe account and delegated the product choice. This service has a professional audience (self-published authors) and the backlog always meant it to carry a small fee.
Decision: One paid feature, the Batch Fixer (`app/batch-fixer`, `lib/batch-fix.ts`): $5 one-time via Stripe Checkout with an inline price (`lib/batch-price.ts`; `STRIPE_PRICE_ID` optional). `app/api/verify` retrieves the session server-side and sets a 12-month HMAC-signed HttpOnly cookie (`lib/access-token.ts`); the success URL doubles as a restore link. No accounts, no database, no webhook; files still never leave the browser.
Rejected: Payment Link (no way to gate anything); webhooks + a store (needs persistence for a $5 product); a catalog product created in the dashboard (the harness blocks dashboard writes and API calls that create Stripe objects).
Consequence: Possession of the restore link is the entitlement; `ACCESS_TOKEN_SECRET` and `STRIPE_SECRET_KEY` live only in the host `.env`. Rotating the secret logs every buyer out until they reopen their restore link. Live mode is an Owner decision (trade-licence and VAT exposure).
Evidence: `tests/unit/access-token.spec.ts`, `tests/unit/batch-fix.spec.ts`, `tests/e2e/batch-fixer.spec.ts`.

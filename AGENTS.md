# epub-metadata-fixer — project conventions

Read `HANDOVER.md` first: current state, decision record (especially D1's
EPUB-spec sourcing, D2's mimetype/OCF rebuild safety, and D3's cover-size
sourcing caveat), next steps. Goal in `GOALS.md` (G-001). Parent initiative
in `E:\CLAUDE\projects\svc-lab\`; company-wide standards in
`E:\CLAUDE\COMPANY\`.

- Stack: Next.js App Router, TypeScript, Tailwind. No database, no auth,
  no accounts. Every EPUB/image is parsed and rewritten client-side in the
  browser via JSZip — no API routes, nothing is ever sent to a server.
- `lib/epub-zip.ts` is the only place that should touch JSZip directly.
  `exportEpub()` rebuilds the whole zip explicitly (mimetype first, stored
  uncompressed, every other entry copied in original order) rather than
  calling `zip.generateAsync()` on a mutated in-place zip — this is the
  fix for a real EPUB OCF requirement (mimetype must be the physically
  first entry, uncompressed), not decoration. Don't bypass it with a
  simpler-looking direct `zip.file(path, content); zip.generateAsync()`
  call, even though it would work for most readers most of the time.
- `lib/epub-metadata.ts`'s `buildFixedOpf()` does targeted regex-scoped
  string surgery on the OPF, not a full parse-and-reserialize round trip —
  deliberate, so a service's manifest/spine content that this tool doesn't
  understand can't get silently reformatted or corrupted. Don't replace it
  with a generic XML-library round trip without re-reading D2's reasoning
  in `HANDOVER.md` and re-running the full test suite against real-world
  sample EPUBs, not just the synthetic fixtures.
- `lib/image-dimensions.ts` and `lib/cover-requirements.ts` only support
  PNG and JPEG (the two formats storefronts actually accept) — no need to
  add GIF/WebP/etc. unless a real backlog reason shows up.
- `npm install`/`npm ci` need `--legacy-peer-deps` (a live npm/arborist
  bug, not specific to this project — see `svc-lab/HANDOVER.md`).
- Two test layers: `npx vitest run` (unit) and `npx playwright test`
  (e2e — real file-upload and triggered-download assertions for all three
  tools, against binary fixtures generated by
  `npm run generate-fixtures`). Both must pass before calling a change
  done; also run `npm run build` — it catches server/client boundary bugs
  that `next dev`, ESLint, and TypeScript don't.
- See `E:\CLAUDE\COMPANY\INFRASTRUCTURE_DEPLOY.md` for the redeploy
  command once live.
